# 3.0.0-beta.1 External Service Compatibility Validation

Date: 2026-10-16. Scope: local Facilitator, Gateway, and Catalog end-to-end flows and old/new SDK interoperability. External services were not deployed or published. All SDKs used exact npm registry versions.

## Outcome

After the required integration migration, v2 HTTP messages, resource extension v1 wire format, existing configuration, and resource ledgers remained usable within the validated scope. **Source compatibility requires more than replacing dependencies:** Facilitator must use official Core consistently and migrate resource imports and registration factories; Gateway must migrate its HTTP codec.

**Local isolation and live Nile testing against the current official deployment completed:** ordinary Permit2, upto, batch, GasFree, and low-allowance dual-resource sponsorship/reclamation passed. The official deployment does not expose its SDK/build version, so this does not prove deployment and live-chain acceptance of the upgraded local Facilitator. EVM broadcasts were outside this Nile test.

Direct Facilitator dependency replacement reproduced private-type conflicts between old and new Core, moved resource exports, and legacy extension factories lacking verify/execute callbacks. Discovery data cannot replace asset, amount, payTo, timeout, and extension declarations in Gateway 402s.

## Issues found and fixed

- Official EVM registration helpers also registered 24 v1 networks, making `/supported` inconsistent with the service's v2-only HTTP capability. Registering v2 classes per configured network fixed this; complete supported-set tests failed before the fix and passed afterward.
- Official EIP-3009 verify removed legacy exception normalization, turning malformed input from protocol failures into HTTP 500s. The service restores prior status/error codes only in that verify branch, with fixed descriptions. Official implementations still own Permit2/settle. Malformed input, real signatures, and RPC fault regressions passed; no claim of restoring all legacy settle error text.
- **Live Nile testing found Gateway's default 10-second timeout insufficient:** the first sponsored request returned 504 after official settlement succeeded, without upstream delivery. Original nonce/txID reconciliation confirmed no duplicate payment. The fix uses `max(240000, global timeout)` only when a resource-enabled TRON exact Permit2 route actually carries the extension; dedicated `X402_GATEWAY_RESOURCE_SPONSORING_TIMEOUT_MS` explicitly overrides it. Ordinary requests and inbound windows retain their original values. Fourteen delay/configuration regressions passed; a new zero-allowance payer completed live delivery and reclamation of both resources.

Independent review identified the first two issues; both have failing-then-passing evidence and final full-suite results. The Nile finding was likewise reproduced, covered by regressions, and fixed. Final source and tests remain on the branches, without push, merge, or deployment.

## Interoperability and recovery

- Real SDK2 exact signatures → new Gateway/Facilitator → successful settlement/delivery. Static real SDK2 upto/batch deposit/voucher signatures also passed upgraded HTTP/Core verification, claim, and actual-amount settlement.
- SDK3 ordinary signature → old SDK2 mechanism → success. SDK3 signed Approval → old/new Core, mechanism, and extension combinations with equivalent capabilities → one sponsorship, settlement, and delivery.
- Legacy Facilitator without a resource runtime returns `sponsor_runtime_unavailable`, reflecting capability configuration differences.
- Official EVM Base EIP-3009 and GasFree local HTTP relayer flows passed with injected chain broadcast/confirmation.
- Facilitator real HTTP tests cover TRON upto actual settlement amounts, zero amounts, excessive amounts, invalid signatures, replay, and pending; batch deposit/voucher/claim/settle/refund, zero management timeout, authorizer signatures, invalid signatures, chain failures, and state results passed. Existing Gateway/Catalog routes do not include upto/batch.
- Joint flows use the actual Catalog handler and Gateway/Facilitator loopback sockets, real TIP-712/Approval validation, PostgreSQL settlement/seller isolation/advisory locks, and SQLite ledgers. Duplicate nonces, invalid signatures, and invalid HTTP fields are rejected; upstream delivery occurs only after successful settlement.
- Dual energy/bandwidth delegation → Approval → settle → reclamation passed, with ledger records written before broadcast. Unfinished debts from SDK2 and SDK3 runtimes were recovered by SDK3 after closing and reopening SQLite, without rebroadcasting Approval. Storage format and implementation were unchanged; only resource type imports migrated.
- Real service regressions cover PostgreSQL shared coordination, concurrent budgets/capacity, restarts, RPC/lock-connection failures, original txID recovery, permissions, and reclamation anchoring.

## Limitations and subsequent acceptance

The joint Catalog fixture maps production discovery addresses/networks to local Nile routes with fixed test prices. This does not establish live deployment, production pricing, or public business API availability. Local joint tests explicitly inject chain reads/broadcast/confirmation and resource visibility; wallet signing, SDK/Core, HTTP, and database logic run for real. The Nile section uses live chain I/O.

The batch ChannelManager's raw refund management message `extra:{}` lacks authorizer metadata for `/verify`, while direct `/settle` works. SDK2 behaves the same, and the manager itself uses `/settle`; this is not a new regression. The beta's known optimistic upto preflight on balance/allowance RPC errors was not changed in this service migration.

Acceptance of a deployed upgraded Facilitator requires identifying its SDK/build version and running separate deployment acceptance. This run did not restart the official service or access its private resource ledger. Recovery/concurrency/lock-failure evidence comes from local real-storage tests; chain evidence confirms actual delegation, Approval, settlement, and reclamation only. Gateway added no cross-instance automatic delivery/idempotent recovery. After arbitrary network interruption, reconcile the original nonce/txID before creating a new payment. No acceptance claim is made for official EVM pending-store cross-instance/restart recovery or live TRON custom EIP-3009 tokens.
